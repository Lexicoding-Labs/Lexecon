# Security scan triage for this local candidate

The owner-requested Codex Security Cloud scan completed on 2026-10-04 against source revision `05f409a8cb441fb422d5857c8bf2a752f9df6dd1` and reported 34 findings (20 high, 12 medium, 2 low). Its findings are claims about that older revision, not a scan of this candidate. They were used to guide local code inspection and regression checks; their cloud status has not been changed.

| Scan themes | Candidate evidence and disposition |
| --- | --- |
| Public decisions, tool scope, policy changes, audit/evidence exports, governance and oversight routes | The current app mounts these routers behind session, audit-permission, or admin dependencies in `src/lexecon/api/server.py`. Decision grants require policy permission for the requested tool and online verification. The local proof and `tests/test_security_regressions.py` exercise these boundaries. |
| SPA traversal, permissive policy matching, ignored conditions, high-risk policy mode, partial policy loads, modified decision verification | Containment, fail-closed matching, atomic loads, and response binding have regression coverage in `tests/test_security_regressions.py`; the browser example also checks responses against ledger entries. |
| Named limiter deadlock, forwarded-header trust, sessions surviving credential changes, OIDC email linking, password expiry, lockout and account enumeration | Focused regressions in `tests/test_security_regressions.py` and `tests/test_supported_mode.py` passed. MFA-enabled legacy accounts fail closed, but there is no supported HTTP enrollment or challenge-completion journey. |
| Export tenant labels, unsigned or falsely verified bundles, arbitrary evidence signing | The supported API accepts only tenant `default`; evidence ZIP export and verification have focused tests. The verifier explicitly distinguishes rehashing from signature authenticity and complete source-chain verification. Admin-created governance evidence is not represented as independently authenticated source truth. |
| Tracked signing keys and credentialed Terraform workflow | The candidate has fresh local history and contains neither old key blobs nor the infrastructure workflow/templates. The [local history investigation](signing-key-history.md) identifies two historical source keys and their introduction/deletion commits. The new read-only guard passes on this candidate and blocks the original source, with 15 focused regression tests. Whether external consumers trusted the historical keys still requires owner confirmation; no rotation or remote cleanup is claimed. |
| CLI key file permissions, default setup credentials, demo seed | Focused tests cover owner-only CLI key permissions and password-selected setup. The seed endpoint is session-gated and tags events as synthetic; the portfolio walkthrough uses real policy evaluations. |

`pytest -q -o addopts='' --disable-warnings tests/test_security_regressions.py tests/test_supported_mode.py` passed 25 tests on this candidate. The full Python suite passed 1,209 tests with 8 skips. This evidence supports a **local, single-organization demonstration**, not a claim that every scan finding is fixed for a multi-tenant hosted deployment. In particular, global governance stores lack verified tenant predicates, risk and evidence semantics require trusted operators, no external tool is gated by the prototype beyond its harmless reference adapter, and historic signing-key use remains unresolved.
